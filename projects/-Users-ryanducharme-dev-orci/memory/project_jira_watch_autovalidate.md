Building an autonomous validation loop at `~/.claude/jira-watch/` (started 2026-08-13). A launchd watcher detects tickets arriving in the Jira "Ready for Testing" column, a single-flight runner creates the worktree and spawns a Claude session running `/workon` in VALIDATE mode, and a shell gate transitions the ticket to Done.

**Decisions Ryan made:** full autonomy (no per-ticket approval); review is an **EOD digest only** (~17:30, one summary of closed/blocked/inconclusive); autonomous runs do the **full close-out including the draft PR**.

**The gate is mechanical, not confidence-based.** An LLM's self-reported confidence is not a control. The session's job is to emit a result JSON (`verdict`, `app_build_sha`, `merge_commit`, and `evidence` for positive / negative / red_check); `gate.sh` refuses to transition if the verdict isn't deploy-ready, any evidence field is empty, or the build SHA doesn't contain the merge commit. **This means the autonomous path must suppress `/workon` close-out step 6** — the skill has the model transition the ticket, which would defeat the gate. Interactive `/workon` is unchanged. See [[feedback_validation_protocol]] and [[feedback_green_light_closeout]].

**Build order (riskiest first):** 1 headless-MCP probe ✅, 2 `jira.sh`+`watch.sh` dry-run ✅, 3 extract `worktree-create.sh` and rewire `workon` ✅, 4 app-freshness preflight (`freshness.sh` ancestry check + rebuild/restart of a dedicated main instance), 5 session spawn **plus extracting `worktree-done` into `~/.claude/bin/worktree-teardown.sh`** — the runner must be able to tear down after an aborted run and must never call zsh rc functions (a stale interactive shell silently turned the self-verify helper into a no-op while the command still looked successful), 6 `gate.sh`, 7 `digest.sh`.

**What this actually is:** a ticket-driven agentic work dispatcher, not one loop. Four pluggable parts — **selector** (JQL), **mode** (VALIDATE / IMPLEMENT / TRIAGE), **gate** (what evidence admits a write), **cadence/concurrency**. "Ready for Testing → validate" is the first policy over that machine. Second planned policy: sweep Ryan's non-Done reporter backlog in **TRIAGE** mode (output = disposition + evidence, not code). Key asymmetry — triage is read-only investigation, so it needs no worktree and no running app and can run concurrently, whereas VALIDATE is pinned to one app instance and must stay single-flight. Level-triggered backlog work also needs a cursor and a daily budget instead of the edge-triggered seen-file.

**MCP works headlessly.** `env -i ... claude -p` with a stripped environment still reached the Atlassian connector and returned OR-2743's status, so connectors authenticate at account level, not per interactive session — despite `~/.claude.json` listing no `mcpServers`. Two consequences: the session layer can use the rich Jira MCP tools for context pull, and the spawned session also has `transitionJiraIssue`/`addCommentToJiraIssue` within reach. Enforce the gate structurally with `claude --disallowed-tools mcp__claude_ai_Atlassian__transitionJiraIssue mcp__claude_ai_Atlassian__addCommentToJiraIssue` rather than by prompt instruction; `gate.sh` then owns both the comment and the transition. Unknown names in `--disallowed-tools` no-op silently, so verify the denial actually fires once before going live (per [[feedback_security_review]]).

**Hard-won facts:**
- `POST /rest/api/3/search` returns **410 Gone** (removed 2025). Use `/rest/api/3/search/jql`, which returns `{issues, isLast, nextPageToken}` and must be paginated.
- `project = OR` **must be quoted** in JQL — bare `OR` is a keyword and the query 400s.
- Scope with `sprint in openSprints()` — cleanly excludes the 7 stale 2025-era tickets parked in the column.
- `status CHANGED TO` alone **also matches tickets that already left the column** (4 of 14 were Done). Must AND `status = "Ready for Testing"` with the CHANGED TO clause.
- `gh pr list --search "OR-NNNN"` **over-matches** — it hits any PR whose body mentions the key, including sibling PRs in a series and unrelated ancient ones (OR-2736 matched both #4313 and #1196). Filter to a "strong" match: ticket key in the PR title, or `Fixes|Closes|Resolves OR-NNNN` in the body. With that filter each ticket resolves to exactly one PR. An earlier read that #4272 was an umbrella PR spanning OR-2715/2716/2717/2718 was wrong — #4272 is OR-2715's own PR; the four are separate PRs in one websocket series, so per-ticket fan-out is correct for them.
- Chain grouping therefore only needs the honest case: a single PR carrying several `Fixes` lines. Detect that from the body; no union-find needed. Belongs in the runner, not the watcher.
- `freshness.sh <ticket> <built-ish>` implements the app-freshness gate: resolves the strong-match merged PR(s), then `git merge-base --is-ancestor <merge_sha> <built_sha>`. Exit 0 contained, 4 stale build, 5 no merged PR (nothing to validate), 1 error. Emits the JSON the result record needs. Verified red by checking OR-2743 (merged Aug 7) against an Aug 5 build.
- Arrival rate ~5/day, batches up to 12. Concurrency cap must be 1 — validation is serialized on the local app (port 8080, local Postgres, HL7 injections).
- Pass Jira creds via `curl -K -` on stdin, never `-u` in argv (`ps` exposure) — the old `_jira_branch_prefix` in `~/.zshrc` had this flaw and is now gone.
- Layout: shared libs in `~/.claude/bin/` (`jira.sh`, `worktree-create.sh`), subsystem-only scripts in `~/.claude/jira-watch/bin/`. `workon` in `~/.zshrc` is now a 4-line wrapper that captures the script's stdout and cds; `worktree-create.sh` prints only the directory on stdout and every diagnostic to stderr so that contract holds. Exit codes: 0 created, 1 usage/error, 3 already exists.
- Worktree creation must be all-or-nothing. A failure after `git worktree add` (e.g. the `.env.local` symlink) leaves a worktree + branch behind, and every retry then hits the already-exists guard and strands the ticket. `worktree-create.sh` has an EXIT-trap rollback; verified by forcing the symlink to fail and confirming the branch, directory, and `git worktree list` entry are all gone.
- `QA_ENV_REL` overrides the symlinked config path — needed because the repo hook blocks any command mentioning `.env`, so tests use a neutrally named fixture.
- curl is blocked in Claude's Bash tool for this project, but works fine from inside a script; nested `claude -p` spawns are blocked by the auto-mode classifier, so Ryan runs those probes himself. See [[reference_curl_blocked_use_node_http]].

**Runtime model — ephemeral env per validation** (Ryan's call, and feasible). A blank Postgres is fully usable because the app bootstraps itself end to end: `DatabaseSchemaConfiguration` creates the public schema plus one per *enabled* tenant, `LiquidbaseConfiguration` migrates each, `TenantSetupRunner` seeds tenant rows, `AdminUserSetupRunner`/`DefaultUserSetupRunner` seed logins, and `ApplicationRunner` — `@ConditionalOnProperty("initialize.configuration.enabled", matchIfMissing = true)`, so on by default — imports the bundled clinical config from `orci/src/main/resources/data/` with checksum change detection. No manual SQL, no hand-seeding.

Consequences: no contention with Ryan's own 8080 instance, and **single-flight is no longer a correctness constraint** — concurrency is bounded only by laptop resources (Postgres + Valkey + JVM per env). `env-up.sh <run-id> <jar>` / `env-down.sh <run-id>` implement this; env-up picks three free ports, prints a JSON descriptor, and exits 6 if containers came up but the app never reported `UP`. Overrides needed: `spring.datasource.{url,username,password}`, `spring.data.redis.{host,port,password}`, `server.port`, and the `allowed-origins`/`url` pair that is otherwise hardcoded to 8080. Plaintext passwords pass straight through Jasypt (only `ENC(...)` is decrypted). The ephemeral Valkey **must** keep `--notify-keyspace-events KEA` or session expiry/destroy events silently stop firing. Containers are deliberately not `--rm`: on a failed boot their logs are the only evidence.

**Biggest live risk:** the app-freshness gate. Validation runs against the local main build, which is routinely stale (observed: 8080 process a day older than origin/main). Without the preflight, the loop confidently green-lights fixes absent from the running JAR. See [[reference_stale_local_app_build]].
