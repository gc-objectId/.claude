Building an autonomous validation loop at `~/.claude/jira-watch/` (started 2026-08-13). A launchd watcher detects tickets arriving in the Jira "Ready for Testing" column, a single-flight runner creates the worktree and spawns a Claude session running `/workon` in VALIDATE mode, and a shell gate transitions the ticket to Done.

**Decisions Ryan made:** full autonomy (no per-ticket approval); review is an **EOD digest only** (~17:30, one summary of closed/blocked/inconclusive); autonomous runs do the **full close-out including the draft PR**.

**The gate is mechanical, not confidence-based.** An LLM's self-reported confidence is not a control. The session's job is to emit a result JSON (`verdict`, `app_build_sha`, `merge_commit`, and `evidence` for positive / negative / red_check); `gate.sh` refuses to transition if the verdict isn't deploy-ready, any evidence field is empty, or the build SHA doesn't contain the merge commit. **This means the autonomous path must suppress `/workon` close-out step 6** — the skill has the model transition the ticket, which would defeat the gate. Interactive `/workon` is unchanged. See [[feedback_validation_protocol]] and [[feedback_green_light_closeout]].

**Build order (riskiest first):** 1 headless-MCP probe ✅, 2 `jira.sh`+`watch.sh` dry-run ✅, 3 extract `worktree-create.sh` and rewire `workon` ✅, 4 app-freshness preflight (`freshness.sh` ancestry check + rebuild/restart of a dedicated main instance), 5 session spawn **plus extracting `worktree-done` into `~/.claude/bin/worktree-teardown.sh`** — the runner must be able to tear down after an aborted run and must never call zsh rc functions (a stale interactive shell silently turned the self-verify helper into a no-op while the command still looked successful), 6 `gate.sh`, 7 `digest.sh`.

**What this actually is:** a ticket-driven agentic work dispatcher, not one loop. Four pluggable parts — **selector** (JQL), **mode** (VALIDATE / IMPLEMENT / TRIAGE), **gate** (what evidence admits a write), **cadence/concurrency**. "Ready for Testing → validate" is the first policy over that machine. Second planned policy: sweep Ryan's non-Done reporter backlog in **TRIAGE** mode (output = disposition + evidence, not code). Key asymmetry — triage is read-only investigation, so it needs no worktree and no running app and can run concurrently, whereas VALIDATE is pinned to one app instance and must stay single-flight. Level-triggered backlog work also needs a cursor and a daily budget instead of the edge-triggered seen-file.

**MCP works headlessly.** `env -i ... claude -p` with a stripped environment still reached the Atlassian connector and returned OR-2743's status, so connectors authenticate at account level, not per interactive session — despite `~/.claude.json` listing no `mcpServers`. Two consequences: the session layer can use the rich Jira MCP tools for context pull, and the spawned session also has `transitionJiraIssue`/`addCommentToJiraIssue` within reach. Enforce the gate structurally with `claude --disallowed-tools mcp__claude_ai_Atlassian__transitionJiraIssue mcp__claude_ai_Atlassian__addCommentToJiraIssue` rather than by prompt instruction; `gate.sh` then owns both the comment and the transition. Unknown names in `--disallowed-tools` no-op silently, so verify the denial actually fires once before going live (per [[feedback_security_review]]).

**Hard-won facts:**
- `POST /rest/api/3/search` returns **410 Gone** (removed 2025). Use `/rest/api/3/search/jql`, which returns `{issues, isLast, nextPageToken}` and must be paginated.
- `project = OR` **must be quoted** in JQL — bare `OR` is a keyword and the query 400s.
- Scope with `sprint in openSprints()` — cleanly excludes the 7 stale 2025-era tickets parked in the column.
- `status CHANGED TO` alone **also matches tickets that already left the column** (4 of 14 were Done). Must AND `status = "Ready for Testing"` with the CHANGED TO clause.
- `gh pr list --search "OR-NNNN"` **over-matches** — it hits any PR whose body mentions the key, including sibling PRs in a series and unrelated ancient ones (OR-2736 matched both #4313 and #1196). Filter to a "strong" match: ticket key in the PR title, or `Fixes|Closes|Resolves OR-NNNN` in the body. With that filter each ticket resolves to exactly one PR. An earlier read that #4272 was an umbrella PR spanning OR-2715/2716/2717/2718 was wrong — #4272 is OR-2715's own PR; the four are separate PRs in one websocket series, so per-ticket fan-out is correct for them.
- Chain grouping therefore only needs the honest case: a single PR carrying several `Fixes` lines. Detect that from the body; no union-find needed. Belongs in the runner, not the watcher.
- `freshness.sh <ticket> <built-ish>` implements the app-freshness gate: resolves the strong-match merged PR(s), then `git merge-base --is-ancestor <merge_sha> <built_sha>`. Exit 0 contained, 4 stale build, 5 no merged PR (nothing to validate), 1 error. Emits the JSON the result record needs. Verified red by checking OR-2743 (merged Aug 7) against an Aug 5 build.
- Arrival rate ~5/day, batches up to 12. Concurrency cap must be 1 — validation is serialized on the local app (port 8080, local Postgres, HL7 injections).
- Pass Jira creds via `curl -K -` on stdin, never `-u` in argv (`ps` exposure) — the old `_jira_branch_prefix` in `~/.zshrc` had this flaw and is now gone.
- Layout: shared libs in `~/.claude/bin/` (`jira.sh`, `worktree-create.sh`), subsystem-only scripts in `~/.claude/jira-watch/bin/`. `workon` in `~/.zshrc` is now a 4-line wrapper that captures the script's stdout and cds; `worktree-create.sh` prints only the directory on stdout and every diagnostic to stderr so that contract holds. Exit codes: 0 created, 1 usage/error, 3 already exists.
- Worktree creation must be all-or-nothing. A failure after `git worktree add` (e.g. the `.env.local` symlink) leaves a worktree + branch behind, and every retry then hits the already-exists guard and strands the ticket. `worktree-create.sh` has an EXIT-trap rollback; verified by forcing the symlink to fail and confirming the branch, directory, and `git worktree list` entry are all gone.
- `QA_ENV_REL` overrides the symlinked config path — needed because the repo hook blocks any command mentioning `.env`, so tests use a neutrally named fixture.
- curl is blocked in Claude's Bash tool for this project, but works fine from inside a script; nested `claude -p` spawns are blocked by the auto-mode classifier, so Ryan runs those probes himself. See [[reference_curl_blocked_use_node_http]].

**Runtime model — ephemeral env per validation** (Ryan's call, and feasible). A blank Postgres is fully usable because the app bootstraps itself end to end: `DatabaseSchemaConfiguration` creates the public schema plus one per *enabled* tenant, `LiquidbaseConfiguration` migrates each, `TenantSetupRunner` seeds tenant rows, `AdminUserSetupRunner`/`DefaultUserSetupRunner` seed logins, and `ApplicationRunner` — `@ConditionalOnProperty("initialize.configuration.enabled", matchIfMissing = true)`, so on by default — imports the bundled clinical config from `orci/src/main/resources/data/` with checksum change detection. No manual SQL, no hand-seeding.

**No executable jar exists** — `spring-boot-maven-plugin` only runs `build-info`, there is no `repackage` goal, and Ryan runs local dev IDE-style (`java -cp target/classes … OrciApplication`). So `java -jar` can never work. The app ships as a Jib image: `mvn -B -P build-image -DskipTests -Dbuild.image.tag=<tag> -pl orci -am package jib:dockerBuild` from a detached main worktree at `~/dev/worktrees/_loop-main`. The `build-image` profile is config-only with no phase binding, so the goal must be named explicitly — and it must be `jib:dockerBuild`, never `jib:build`, which would push to a registry. Build takes ~40s warm. It also re-tags `guidedclinical/orci:latest` as a side effect.

The env is a per-run compose project (`docker compose -p orci-loop-<run-id> -f ~/.claude/jira-watch/compose-loop.yml`), reusing the existing `docker` Spring profile whose `application-docker.yml` already points the datasource at `postgres:5432` and redis at `redis`. Three things had to change from `orci/docker-compose.yml` for multi-run isolation: drop `container_name` (it defeats compose's project prefixing), publish no host ports for postgres/redis (only the app), and use tmpfs instead of the `~/tmp/postgres-data` volume. Service names must stay `postgres`/`redis` — `application-docker.yml` resolves them by DNS. Profile order `local,docker` is deliberate and verified: docker is last so its datasource/redis win, while local supplies tenant enablement — confirmed by `mayo-mayo` appearing in the created schemas (mayo is `enabled: false` in application.yml, true only in application-local.yml).

Consequences: no contention with Ryan's own 8080 instance, and **single-flight is no longer a correctness constraint** — concurrency is bounded only by laptop resources (Postgres + Valkey + JVM per env). `env-up.sh <run-id> <jar>` / `env-down.sh <run-id>` implement this; env-up picks three free ports, prints a JSON descriptor, and exits 6 if containers came up but the app never reported `UP`. Overrides needed: `spring.datasource.{url,username,password}`, `spring.data.redis.{host,port,password}`, `server.port`, and the `allowed-origins`/`url` pair that is otherwise hardcoded to 8080. Plaintext passwords pass straight through Jasypt (only `ENC(...)` is decrypted). The ephemeral Valkey **must** keep `--notify-keyspace-events KEA` or session expiry/destroy events silently stop firing. Containers are deliberately not `--rm`: on a failed boot their logs are the only evidence.

**Verified step 4 numbers:** Jib image build ~40s warm, app `Started OrciApplication` in ~56-59s, so ~65s wall clock from `env-up.sh` to a usable app. No DB-snapshot optimisation needed. Readiness must be detected from the `Started OrciApplication in` log line, **not** `/actuator/health` — that endpoint sits behind Spring Security and returns 403, and Tomcat begins serving before `ApplicationRunner` finishes importing clinical config, so an HTTP-based probe can report ready while imports are still running.

**Ephemeral env credentials:** `admin.password: admin` is set in `application.yml`, so admin/admin exists for API work. `DefaultUserSetupRunner` needs all three of `default_user_username`/`default_user_password`/`default_user_email` or it skips silently, leaving no ROLE_USER for UI validation — `compose-loop.yml` now passes them via `JVM_FLAGS -D` (not env vars, because `@Value` reads those literal underscored names). Result: `admin` (ROLE_ADMIN) + `loopuser` (ROLE_USER). Epic OAuth is disabled in this env, so Epic-dependent paths do not exercise.

**CI reuse (Ryan's question, answered yes):** the same compose file + Jib image could run the pre-merge PR gate inside the runner — a different shape from the rejected AWS per-PR-env work (OR-2452, OR-2494/2507 WON'T DO), needing no provisioned infra. Caveats: cold CI builds are 5-10min without ~/.m2 and npm caching; CI should get its own `ci` Spring profile rather than borrowing `local` (which enables the mayo tenant); standard 2-CPU runners are tight for app+PG+Valkey; qa-suite resolves envs via `.env` files pointing at deployed hosts, so BASE_URL plumbing and API-based seeding would be needed. See [[project_premerge_ci_gate]].

**Component inventory** (all in `~/.claude/bin/` unless noted; `~/.claude/jira-watch/bin/` for subsystem-only):
`jira.sh` (read-only REST helpers + `jira_slug`), `worktree-create.sh`, `worktree-teardown.sh`, `freshness.sh`, `build-image.sh`, `env-up.sh`, `env-down.sh`, `gate.sh`; subsystem: `watch.sh`, `runner.sh`, `digest.sh`, `compose-loop.yml`, `prompts/validate.md`.

**The result record is split in two on purpose.** `runner.json` holds runner-owned facts (ticket, image, sha, base_url, freshness); `session.json` holds only session claims (verdict, evidence, blockers, automation, jira_comment). The session cannot write the fields the gate checks, and `gate.sh` re-runs `freshness.sh` itself rather than trusting either file. Gate refusal criteria: verdict must be `deploy-ready`, all three evidence fields non-empty and ≥60 chars, freshness re-check green, a citable merged PR, and the ticket still in Ready for Testing/Testing. `gate.sh --commit` is deliberately **unwired** pending review of several dry-run decisions; wiring needs a Jira comment POST plus a transition-ID lookup.

**The runner cannot be launched from inside a Claude Code session** — the auto-mode classifier blocks spawning a nested `claude` with `bypassPermissions` (inconsistently: one invocation slipped through, the retry was denied). Ryan runs it from his shell with `!`, or launchd runs it. This is the correct boundary anyway: the dispatcher is a daemon, not a nested agent.

**Compose project names must be lowercase** — `orci-loop-OR-2743` is rejected outright. `env-up.sh`/`env-down.sh` lowercase the run-id internally. Lowercase test run-ids hid this until the runner used a real ticket key.

**First trial (OR-2743, 2026-08-14) succeeded.** 24min session, verdict deploy-ready, gate admitted in dry-run. The session wrote node HTTP scripts, created a patient/case, started it via `POST /api/app-launch`, ran an insulin infusion, posted eGFR+GLUCOSE observations, read `rule_fired_results.EXPANDED_CALCULATION`, and confirmed the alert through the user-facing API. **It invented a stronger red check than the prompt specified:** compiled the parent commit's version of the changed class, swapped it into `/app/classes` in the running container, restarted, reproduced the exact Sentry NPE, then restored (checksum-verified) and restarted. Independently corroborated: the shipped class's LineNumberTable has no line 209 (206→211), so a `:209` frame is impossible from it. Lombok is **not** on the runtime classpath, so in-place compilation needs `@Slf4j` replaced with an explicit logger. Both techniques are now documented in `prompts/validate.md`.

**Jira transitions wired** (Ryan's request): runner moves the ticket to **Testing** at pickup — which doubles as the in-flight lock, since `watch.sh` only matches `status = "Ready for Testing"` — and `gate.sh` moves it to **Done** at the end, comment first so a Done ticket is never left unexplained. Both gated on `--commit`; dry-run logs what it would do. Transition IDs are Testing=2, Ready for Testing=3, Done=31, but `jira_transition_to` resolves by target status *name* because available transitions depend on current status. Comments post via **API v2**, not v3 (v3 demands ADF), so markdown link syntax will not render — post bare URLs. On failure the ticket deliberately **stays in Testing** rather than reverting, so a repeatedly-failing ticket cannot loop through the watcher.

**Env gap the trial found:** the seeded ROLE_USER has an empty `allowed_tenants` (a `json` column), so the session had to grant itself tenant access. `env-up.sh` now seeds all enabled tenants after boot.

**Gate hardened against fluent fabrication (done).** `session.json` must include `red_check_signature`: a verbatim substring of the application log that appeared only while the red check was active, ≥20 chars. `runner.sh` captures `docker logs <project>-orci-1` into `<run-dir>/app.log` before the gate runs (container logs die with the container), and `gate.sh` refuses unless that signature is actually present via `grep -qF`. Verified all three ways: real NPE signature admits, a plausible-but-absent signature refuses, and `"ERROR"` refuses as too generic. This turns the central claim from prose into something checkable — the remaining prose fields are still unverifiable by construction.

**Still unverified:** whether `--disallowed-tools` actually suppresses the named MCP tools rather than silently no-opping on unrecognised names. Decisive probe is a control/treatment pair — ask a session whether it has `mcp__claude_ai_Atlassian__transitionJiraIssue` with and without the flag; only YES-then-NO proves the denial bites.

**First full `--commit` run succeeded end to end (OR-2743, 2026-08-14):** moved to Testing at pickup, validated in 11 minutes (down from 24 — the prompt now hands the session the class-swap technique, the lombok gotcha, and pre-granted tenant access), red-check signature verified against the captured log, no tampering detected, comment posted, transitioned to Done, worktree and containers torn down clean.

**Jira comments must be plain text.** The v2 endpoint does not render markdown, so the first posted comment shows literal `\*\*` and escaped backticks on a public ticket. Fixed in two places: the prompt demands plain text with no markdown syntax, and `gate.sh` strips `**` and backticks before posting. Proper fix if formatting is ever wanted is ADF via v3.

**Concurrency bug found before it bit:** `build-image.sh` checks out and compiles in the *shared* `_loop-main` worktree, so two runners would race. It now takes a `${BUILD_TREE}.lock` and waits (up to 900s) rather than failing — the other build usually produces the very image the waiter wants. Environments themselves are per-run isolated, so overlapping runners are otherwise safe.

**`dispatch.sh` and the launchd plists were blocked by the auto-mode classifier** — writing a script whose purpose is running unattended agents against real tickets on a timer needs Ryan's explicit permission grant. Until then the batch form is a shell loop: `for t in A B C; do ~/.claude/jira-watch/bin/runner.sh $t --commit; done`.

**Not yet built — the loop is not autonomous yet.** `runner.sh` takes a single ticket argument; nothing drains `state/queue`, and no launchd plists exist for `watch.sh` or `digest.sh`. Concurrency across simultaneous envs is untested, as is `gate.sh --commit` against real Jira and the runner's Testing transition.

**Known wrinkle to fix:** `runner.sh` should stamp a `running` record into `result.json` at start; otherwise a stale record from a previous run of the same ticket survives a hard failure and the digest misreports it. Never edit `runner.sh` while an instance is executing — `sh` reads scripts incrementally.

**Biggest live risk:** the app-freshness gate. Validation runs against the local main build, which is routinely stale (observed: 8080 process a day older than origin/main). Without the preflight, the loop confidently green-lights fixes absent from the running JAR. See [[reference_stale_local_app_build]].

**Ticket context is injected as a file, not granted as access** (2026-08-24). `runner.sh` writes `<run-dir>/context.md` via `jira_issue_context` — summary, status, assignee, full description, every comment — plus a "previous automated runs" section built from `history.jsonl` (each run archives the prior `result.json` before stamping its own). The prompt tells the session to read it first and to treat prior runs and human comments as work already done. Two payoffs: sessions stop duplicating effort or re-arguing settled points, and the session needs **no Jira credentials at all**, which is what makes a credential-less sandbox viable. Uses Jira API v2 because v3 returns description/comment bodies as ADF.

**Escalation model: an unattended session cannot hold a conversation.** There is nobody to answer it mid-run, so the prompt forbids stalling or guessing: it must record `inconclusive`/`not-deploy-ready` and put each unresolved question in `blockers`, phrased so a human can answer in one line. Those blockers are the only channel to Ryan — surfaced by `digest.sh`, which sorts needs-a-human dispositions (reserved, no_merged_pr, refused, aborted) above the rest. Still missing: any *push* notification; the digest is pull-only.

**A vacation backlog will NOT be picked up by the watcher.** Measured 2026-08-24: 41 tickets in Ready for Testing, 27 of them in open sprints, **0 arrived within the 24h poll window**, 26 within 14 days. The watcher is edge-triggered (`status CHANGED TO ... AFTER -24h`) and the seed step marks current members as seen, so widening the window alone does not help. Needs a second, level-triggered selector: current column membership, oldest first, a per-run budget, and a "skip unless status or comment count changed since our last run" cursor so refusals do not re-run nightly. ~26 tickets at 12–15 min each is roughly a 6-hour overnight sweep serially.

**Reserved tickets** (`LOOP_RESERVED_PATTERN`, default `^Analytics:`) validate in full but drop every Jira write — no Testing transition, no comment, no Done — because those belong to another reviewer (Alex validates Analytics work). Recorded as disposition `reserved`. Title matching is deliberately weak; a Jira label or component would be the robust signal. Known wrinkle: a reserved ticket never gets the Testing in-flight lock, so a scheduled dispatcher would re-validate it every cycle — needs local suppression before launchd goes on.

**Long runs must be detached.** A `for` loop invoked from Ryan's shell is killed at the 2-minute harness timeout, mid-build, leaving the ticket transitioned to Testing plus a worktree, a branch, and a `running` result record. Launch sweeps as `nohup sh -c '...' > ~/.claude/jira-watch/log/sweep.log 2>&1 &` and follow `log/runner.log` for readable progress; `sweep.log` absorbs the Maven output.

**Two stranding bugs that a killed run exposed** (both fixed in `backlog.sh`): a ticket left in Testing fell outside the selector's `status = "Ready for Testing"` filter and would never be offered again, so the JQL now covers `IN ("Ready for Testing", "Testing")` — the worktree/branch/running guards are what prevent stomping work in progress. And a `running` record from a killed run barred its ticket permanently, so records older than `STALE_RUN_SECONDS` (default 5400) are now treated as stale and the ticket is offered again.

**`notify.sh` reported false success for its first hours.** Slack 302-redirects an invalid webhook path, and `curl --fail-with-body` only fails on 400+, so a misconfigured webhook printed "sent" while delivering nothing. It now requires HTTP 200 *and* a body of exactly `ok`, printing "delivered" only then. Diagnose a webhook without exposing it: a real incoming webhook has three path segments after `/services/`. This was caught only by reading the Slack channel independently — the same lesson as the gate re-running its own freshness check and the red check having to be *seen* red.

**Autonomous validation comments use IMPERSONAL voice** (Ryan, 2026-08-24): "This was validated against...", never "I validated this...". This deliberately diverges from the global CLAUDE.md instruction to write validation comments in Claude's first-person voice, and applies **only** to the autonomous path — interactive `/workon` close-outs keep first person. Reason: the comment posts under Ryan's own Jira account, so first person reads as Ryan claiming he did the validation by hand. Enforced in `prompts/validate.md`.

**Slack escalation is live** (verified from both sides 2026-08-24): webhook in keychain service `slack-webhook-jira-watch`, posting to the private channel `#my-agents` (C0BSG3MT8EQ). `runner.sh`'s `record()` pushes every non-admitted disposition with its blockers; successes stay silent so the channel stays worth reading. Setup requires an app Incoming Webhook (api.slack.com/apps → Incoming Webhooks → Add New Webhook to Workspace → pick the private channel), *not* a Workflow Builder trigger.

**Tickets are assigned at pickup and stay assigned through Done** (Ryan, 2026-08-24). `runner.sh` calls `jira_assign` with `JIRA_ACCOUNT_ID` (default Ryan's `712020:eb570e67-...`) whenever `--commit` is set, outside the transition block so a ticket already in Testing still gets owned. Reserved tickets are skipped along with every other write, since they belong to another reviewer.

**Trio result 2026-08-24:** OR-2723 and OR-2726 admitted → Done with verified red checks; OR-2755 (`^Analytics:`) validated deploy-ready and left completely untouched — still Ready for Testing, 0 comments, unassigned. The reserved rule is proven in practice. OR-2755's session also demonstrated the class-swap limitation and its own workaround: reverting 36 rule classes made the app unbootable (missing enum constant `GuidanceCategory.DIABETES_MANAGEMENT`), and it recovered by sourcing a lombok jar to compile in-container, then restored all 41 class files with md5 verification.

**Open design question — self-declared caveats.** OR-2723 was admitted as deploy-ready while its own comment disclosed that Epic was a local stub (no Mayo OAuth keys in the ephemeral env). The gate has no notion of a declared limitation. Proposed: an optional `caveats` field that produces disposition `admitted_with_caveats`, surfaced at the top of the digest and pushed to Slack — but explicitly **not** a refusal, because punishing disclosure would teach the next session to omit it.

**Run of 8 (2026-08-24 evening) — results and what they taught.** 5 closed with caveats, 2 refused, 1 no_merged_pr, 0 clean. Findings:
- **Caveats were universal**, so the flag stopped discriminating. Fixed with a `ship_risk` field (`none` | `material`): the session states whether any caveat should make a reviewer hesitate, and only `material` produces disposition `admitted_with_caveats`. Caveats are still always posted to the ticket as documentation. Marking everything material would recreate the noise problem, and the prompt says so.
- **OR-2691** (Slack deploy notifications) claimed `deploy-ready` but its red-check signature was absent from the app log, so the gate refused. Correct catch: the ticket has no app surface to exercise and should have self-reported `inconclusive`. Tickets with no runtime surface are a category the prompt still handles poorly.
- **OR-2656** was moved to Testing and assigned *before* the freshness check found no merged PR — a board change for a run that never happened. Pickup (transition + assign) now happens **after** freshness.
- **OR-2603** (Alex's Analytics ticket) returned `inconclusive` with four sharp blockers naming exactly what only a human could answer. Reserved rule held: still assigned to Alexandra Wolfe, untouched.

**Tooling added for the human side:**
- `digest.sh` — window is now **last 24h**, not the calendar day (a calendar default showed nothing during the morning review of an overnight sweep). `digest.sh <TICKET>` prints everything about one run: disposition, verdict, blockers, caveats, evidence. `--since DATE` / `--all` also supported.
- `unblock.sh` — walks each needs-a-human ticket and turns it into a decision: (a) answer the blockers in `$EDITOR`, posted as a Jira comment, which both records the answer and makes `backlog.sh` re-offer the ticket, since it re-runs anything whose comment count changed; (r) retry as-is, by deleting `result.json` so it reads as never-run; (s) skip permanently via `state/skip`, which `backlog.sh` honours; (p) send back to In Progress; (n) next; (q) quit.
- `reap.sh` — clears worktrees stranded by a hard-killed run, which otherwise block their ticket forever via the "worktree exists" guard. Conservative: only touches worktrees with a results directory, no live run, no commits ahead of origin/main, and a clean tree. Verified it both fires and leaves hand-made worktrees alone.
- `loopcmd` (in `~/.local/bin`, modelled on `ccmd`) — tmux watch tower: runner log, live dashboard, app log following whichever container is up. Uses `tmux -CC` only under iTerm; anywhere else `-CC` dumps raw control protocol and looks like a hang.
